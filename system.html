PHONE CONTROLLER / SYSTEM DECISION 01

A small controller.
One shared room.

Chosen design: a browser controller and a Cloudflare room service, with the host running the big-screen presentation.

GitHub Pages now. Cloudflare for live rooms.

This site is a static mockup. The proposed live system adds a Cloudflare Worker and one Durable Object per room. Hearth’s existing WebRTC media path stays separate. This architecture is selected for prototyping; it has not been implemented or tested across devices.

Why this system

Writing and voting send small messages. A shared room service keeps those messages ordered, preserves a player’s seat after a brief disconnect, and makes one deadline authoritative. It also keeps the phone independent of the host’s local network address. Phones can use Wi-Fi or cellular internet; this still needs real network testing.

Hearth currently uses PeerJS/WebRTC. That can continue to carry cameras, voice and shared media. The controller does not need to establish a media connection just to submit a sentence. RiffRaff’s room protocol remains independent of whether the eventual host is a standalone app or a Hearth activity; the shipping boundary is still open.

Joining

  1. The host creates a session and receives a private host credential plus a public six-letter room code. Six letters are a proposed RiffRaff default, not copied from Quiplash’s four-letter code.
  2. The screen displays a QR containing the public HTTPS join URL and room code. The same code can be typed manually.
  3. The phone enters a name and chooses an available character. The room assigns a player ID and a secret resume credential. A character claim is atomic; two players cannot take the same seat.
  4. The host may lock admission or remove a player. A leaked public room code is not proof of identity. Codes expire with the room and are rate limited; never put host credentials in the QR.

A round, from the phone’s point of view

Regular rounds: two assigned prompts, 90 seconds total. Keep one prompt in focus, with a switch to the other. Submit each answer explicitly. The service reveals anonymous answers in randomized order and grants one vote only to players outside that matchup. Voting remains open for the complete 15 seconds. Authors, vote counts and scores arrive after closure.

Royale: one shared text/photo/comic/message prompt, one answer per player, 90 seconds to write. Provide equivalent image text after its editorial review. Show submitted answers anonymously in a stable shuffled order. Three equal tokens per player can be stacked or split across other players’ answers; confirm the allocation once. The working vote window is 30 seconds. An 8,000-point pool is distributed according to the current rules.

Two humans: Clank takes the third seat with the same eligibility and scoring. It chooses from three prepared replies uniformly and votes randomly among eligible answers. A complete verified Royale reply bank remains a production dependency. This mockup simulates four people and does not run Clank.

Reconnects and honest receipts

  1. Every action carries a session ID, phase ID and unique action ID. The room deduplicates retries and returns the original receipt for an accepted action.
  2. Restore a seat using the secret resume credential, then request the latest permitted snapshot. Snapshot versions prevent stale updates from replacing current state.
  3. Keep unsent text scoped to its room and prompt on that phone. A draft never counts as a server submission. Nothing automatically submits when the connection returns.
  4. If the deadline passed, show “This round has closed. Your draft was not submitted.” If the service already accepted an action, show its receipt without sending it twice.
  5. A host interruption freezes the room at a defined phase boundary or pauses with an announced deadline adjustment. Exact pause rules are a production decision; do not silently restart timers. Host migration is excluded from the first live prototype.

Room service contract

Version the protocol from day one. Initial actions: join, chooseCharacter, resume, submitAnswer, castVote, submitTokens, hostStart, hostReady, leave. Every action receives accepted/rejected with a reason and current phase version. Time limits use server timestamps; clients estimate the displayed countdown from clock synchronization.

The service sends different snapshots to host and players. Unrevealed answers and authors never enter another player’s payload, hidden HTML, accessibility tree or public log. Only the two assigned prompts go to a regular-round writer. Render user text as text, not HTML. Use TLS, scoped host/player credentials, payload limits, room-code rate limits, origin checks and bounded room lifetimes. Persist accepted actions before sending receipts. Clear room state after the documented recovery period; final retention and moderation rules are implementation decisions.

First implementation gates

  1. Two physical phones: iOS Safari and Android Chrome, one on cellular and one on Wi-Fi, with a separate host.
  2. Eight-player session: simultaneous joins, competing character selections, duplicate sends, background/foreground return, out-of-order updates and room expiration.
  3. Privacy and rule checks: no self-votes, no secret answer leakage, expired actions rejected, one receipt per action, score calculations matching the rules.
  4. Real QR scan from a television at typical seating distance, plus manual code entry. Automated decoding of the mockup is useful but not camera proof.
  5. VoiceOver/TalkBack, keyboard-only use, 320 CSS-pixel width, larger text, on-screen keyboards and reduced motion. The current local display controls are proposals, not Quiplash features.
  6. Finalize image descriptions, prompt-to-image joins, Clank replies, room moderation and the shared readiness/timer handshake with the project manager.

What this demo actually does

All interactions stay inside your browser. It stores sample drafts and preferences in session storage, displays simulated receipts, and uses static timer examples. It opens no live room, sends no player content, calculates no game scores and requests no microphone or camera access. It works as a static GitHub Pages site.

Technical basis

GitHub documents Pages as static hosting; Cloudflare documents Durable Objects as a coordination point for WebSocket connections. These capabilities support the design above; they do not prove this proposed game implementation works. GitHub Pages documentation · Cloudflare WebSocket documentation.
